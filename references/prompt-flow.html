Visão geral

Adaptação do framework TLC Spec-Driven para o ecossistema Hapvida — Azure DevOps, WinCVS, regulação ANS, GitHub Copilot Claude. Camada fina sobre o Agile Hapvida 2.0.

Quatro fases adaptativas, com auto-sizing por complexidade: 

┌──────────┐    ┌──────────┐    ┌─────────┐    ┌─────────┐
│ SPECIFY  │ ─► │  DESIGN  │ ─► │  TASKS  │ ─► │ EXECUTE │
└──────────┘    └──────────┘    └─────────┘    └─────────┘
 obrigatório     opcional*       obrigatório**  obrigatório

 *  Auto-skip baseado em complexidade
 **  Sempre obrigatório + sync automático ao Azure DevOps (ADR-010)

Cada prompt command executa um conjunto fixo de passos e produz artefatos rastreados em .specs/. As próximas seções detalham os princípios e o fluxo completo.

Auto-Sizing — princípio central

A complexidade determina a profundidade, não um pipeline fixo. Antes de iniciar qualquer feature, avalie escopo e aplique apenas o necessário. As fases Specify, Tasks e Execute são sempre obrigatórias; Design é auto-skip em mudanças diretas.

Pequeno

≤ 3 arquivos · frase de escopo
SpecifyInline (frontmatter + seções mínimas)
DesignSkip
Tasks1–3 itens, sem diagrama + sync ADO
ExecuteImplementar + verificar

Médio

feature clara · < 10 tasks
SpecifySpec completa
DesignSkip — design inline
Tasks3–10 itens, fases simples + sync ADO
ExecuteImplementar + verificar

Grande

multi-componente
SpecifySpec + IDs de traceability
DesignArquitetura + componentes
TasksDecomposição + dependências + sync ADO
ExecuteImplementar por task + commit atômico

Complexo

ambiguidade · domínio novo
SpecifySpec + Discuss (gray areas)
DesignArquitetura + KVC + pesquisa
TasksDecomposição + paralelismo + sync ADO
ExecuteImplementar + UAT interativo
Válvula de segurança: quando Design é pulado, Tasks sempre começa listando os passos atômicos. Se a decomposição revelar > 5 passos com dependências complexas, PARE e crie design.md formal — a fase Design foi indevidamente pulada.
Quick Mode (atalho TLC) NÃO está no escopo do piloto v0.4 — ver ADR-008.

Flag uncertain "Não sei" é SEMPRE preferível a inventar. Marca [REVISAO] ou [BLOQUEADO].
[GUARDRAIL] Nunca pular para Passo 5 se 1–4 são acessíveis. Passo 5 é SEMPRE marcado como [REVISAO] ou [BLOQUEADO] — nunca apresentado como fato.
[GUARDRAIL] NUNCA inventar APIs, padrões, comportamentos. Se não encontrar, marque a incerteza explicitamente.

Quem dispara o quê

Em todo prompt o TL/desenvolvedor é quem inicia (digita o slash command). Dali em diante, a LLM orquestra a execução, podendo invocar MCPs ou scripts externos. Em pontos críticos, a LLM devolve a palavra ao TL (gates de aprovação).

TL
TL / Desenvolvedor Ação manual humana: digita slash command, responde perguntas, revisa, aprova, faz commit, abre PR, executa GMUD.
LLM
Agente LLM (Copilot/Claude) Executa os passos do prompt: lê arquivos, gera conteúdo, aplica checklists, decide quando parar e perguntar.
MCP
MCP Server / Skill / Tool Tool externa invocada pela LLM: @azure-devops/mcp, MCP Oracle (dba_*), skills (engenharia-reversa-sigo, engenharia-reversa-forms), executáveis em tools/ (parsers).
CLI
Script / CLI local Executado diretamente pelo TL no terminal: scripts/init-spec-project.ps1, checkout CVS, git commit.
GATE
Gate de aprovação A LLM pára e aguarda decisão explícita do TL antes de prosseguir.
Regra geral: nada é publicado externamente (anexo no ADO, criação de Tasks, commit) sem que o TL tenha aprovado. A LLM nunca executa ações irreversíveis sozinha — sempre pede confirmação antes de chamar create_work_item ou upload de attachment.

Descrição detalhada por comando

Cada cartão abaixo descreve o que de fato é executado: inputs, MCPs/skills invocados, passos do agente, arquivos materializados e guardrails. Origem: prompts/*.prompt.md e scripts/init-spec-project.ps1.

/project-init Bootstrap

Bootstrap do framework no repo do squad. Dispara o script scripts/init-spec-project.ps1 e materializa apenas o que é responsabilidade do squad — não copia SKILL.md/prompts/templates do framework (esses ficam no submódulo .specs/framework/, ADR-012).

Fluxo: TL roda no terminal → init-spec-project.ps1 → TL faz commit do scaffold

Input pedido ao TL

  • SquadName — nome curto do squad/projeto
  • Stack — PLSQL | Java | DotNet | Mista
  • AdoOrg — slug ADO (default hapvidalabs · URL https://dev.azure.com/hapvidalabs/)
  • AreaAtuacao — Comercial, Autorização, etc.
  • Flags: -Brownfield, -WithProject, -WithRoadmap, -NoSubmodule, -Force

Ferramentas usadas

PowerShell git submodule UTF-8 sem BOM

Sem MCP. Tudo é local: filesystem + git.

Execução real do init-spec-project.ps1

  1. Verifica pré-condições — diretório é repositório Git? .specs/ já existe? (sem -Force, preserva).
  2. Cria diretórios base: .specs/project/, .specs/features/, .vscode/, .github/.
  3. Gera STATE.md (ADR-009) — esqueleto com Recent Decisions, Active Blockers, Lessons Learned, Quick Tasks, Deferred Ideas, Todos, Preferences (stack, área, MCP ADO=yes).
  4. Gera .vscode/mcp.json com server azure-devops apontando para npx -y @azure-devops/mcp <AdoOrg> (default hapvidalabs → https://dev.azure.com/hapvidalabs/).
  5. Gera .github/copilot-instructions.md — aponta para .specs/framework/SKILL.md, lista contexto do squad e os 5 guardrails inegociáveis (ADR-007, PII, ANS, ADR-AUSENTE).
  6. Gera .vscode/settings.json — habilita chat.promptFiles + chat.promptFilesLocations apontando para .specs/framework/prompts; chat.instructionsFilesLocations para .specs/framework/instructions e .github/instructions.
  7. Gera .vscode/extensions.json com recomendações: github.copilot, github.copilot-chat, ms-azure-devops.azure-pipelines, oracle.sql-developer-for-vscode.
  8. Gera .github/pull_request_template.md — checklist Spec-Driven (Knowledge Verification, ADR aplicável, [ANS]+norma, anonimização, Conventional Commits, snapshot anexado, versão framework).
  9. Opcionais: -WithProject → PROJECT.md (Vision/For/Solves/Goals); -WithRoadmap → ROADMAP.md (Now/Next/Later); -Brownfield → .specs/codebase/ + knowledge-base/; se Stack=PLSQL também cria .specs/reverse-engineering/.
  10. Vincula framework como submódulo (ADR-012): git submodule add -b <ref> <repo> .specs/framework, faz update --init --recursive, captura HEAD e grava manifesto .specs/.framework.json ({repo, ref, commit, pinned_at, adr}).
  11. Imprime resumo com próximos passos (revisar copilot-instructions, autenticar MCP ADO, commit inicial WI-XXXX: chore(spec-driven): scaffold inicial v0.2 (ADR-012)).

/baseline-reverse-engineering Obrigatório PL/SQL

Produz o artefato canônico de engenharia reversa de uma rotina PL/SQL Oracle, persistido como baseline cacheado em .specs/reverse-engineering/plsql/<NOME>/rev-NNN-<TAG>/ (ADR-011). Elimina releitura do código bruto em specs futuras.

Fluxo: TL invoca + nome do objeto → LLM → CVS PRODUCAO ou MCP Oracle dba_source → skill engenharia-reversa-sigo → TL aprova Painel de Decisão

Input esperado

  • Nome do objeto (SCHEMA.NOME)
  • Tipo: procedure | function | package | trigger
  • (Opcional) ID do work item ADO destino
Quando usar: rotina PL/SQL > 2.000 linhas, complexidade alta, refresh de RE marcada [REVISAO], ou antes de Specify de Improvement+Tunning sobre rotina não mapeada.

Ferramentas / Skills

  • Skill engenharia-reversa-sigo (passos 0–6)
  • CVS tag PRODUCAO (fonte primária)
  • MCP Oracle dba_source (fallback com [ATENCAO])
CVS PRODUCAO MCP Oracle (dba_*) skill: engenharia-reversa-sigo

Execução real

  1. Verifica guardrails — confirma origem CVS tag PRODUCAO; bloqueia leitura de tabelas de negócio.
  2. Invoca skill engenharia-reversa-sigo seguindo seu protocolo (Passos 0–6: caracterização → leitura → análise → riscos → painel).
  3. Materializa pré-requisitos em .specs/codebase/knowledge-base/ se ausentes:
    • indice.md
    • catalogo-conceitos-negocio.md
    • catalogo-objetos-plsql.md
    • pendencias-abertas.md
    • riscos-ans.md
  4. Resolve tag CVS PRODUCAO e grava no frontmatter do artefato (baseline_cvs_tag).
  5. Gera artefato a partir de templates/reverse-engineering-template.md em .specs/reverse-engineering/plsql/<NOME>/rev-NNN-<TAG>/reversa-<NOME>.md.
  6. Atualiza índice README-rotina.md da rotina e os catálogos de conhecimento.
  7. Apresenta Painel de Decisão (seção 11 do artefato) ao TL com lista de [ATENCAO] / [BLOQUEADO] / [ANS] para validação com PO/DBA.

/baseline-reverse-engineering-forms Oracle Forms · Experimental

Espelho Oracle Forms do /baseline-reverse-engineering: orquestra o tool tools/forms-extractor (pipeline 2 etapas) + skill engenharia-reversa-forms e produz artefato canônico em .specs/reverse-engineering/forms/<MODULO>/rev-NNN-<TAG>/.

Fluxo: TL invoca + nome do módulo + path .fmb → tool Convert-FmbToXml.ps1 (.fmb→.xml) → tool Extract-FormsMetadata.ps1 (12 relatórios) → skill engenharia-reversa-forms (Passos 2-6) → TL aprova Painel de Decisão

Input esperado

  • Nome do módulo (ex.: T229BCON)
  • Path do .fmb no checkout CVS tag PRODUCAO
  • (Opcional) ID do work item ADO destino

Ferramentas / Skills

  • Tool tools/forms-extractor/Convert-FmbToXml.ps1
  • Tool tools/forms-extractor/Extract-FormsMetadata.ps1
  • Skill engenharia-reversa-forms (Passos 2–6)
  • CVS tag PRODUCAO (fonte do .fmb)
CVS PRODUCAO skill: engenharia-reversa-forms forms-extractor

Pré-requisitos verificáveis (aborta se faltar)

  • .fmb existe no checkout CVS tag PRODUCAO
  • Oracle Forms Developer 10g+ instalado OU JARs do Forms2XML em ORACLE_HOME
  • Tool tools/forms-extractor/ presente (vem do submódulo do framework)

Execução real

  1. Verifica guardrails — confirma origem CVS tag PRODUCAO; bloqueia se Forms Developer ausente.
  2. Resolve tag CVS PRODUCAO e grava no frontmatter do artefato.
  3. Calcula NNN — sequencial zero-padded (lista rev-* existentes do módulo + 1; primeira = 001).
  4. Cria estrutura de diretórios:
    • .specs/reverse-engineering/forms/<MODULO>/README-modulo.md
    • .specs/reverse-engineering/forms/<MODULO>/rev-NNN-<TAG>/raw/
    • .specs/reverse-engineering/forms/<MODULO>/rev-NNN-<TAG>/parsed/
  5. Etapa 1 — Conversão binário → XML via Convert-FmbToXml.ps1. Saída: <MODULO>.xml em raw/.
  6. Etapa 2 — Extração estruturada via Extract-FormsMetadata.ps1 -Format md. Saída: 12 relatórios em parsed/:
    • _RESUMO, _WINDOWS, _CANVAS, _BLOCKS
    • _TRIGGERS, _PROGRAM_UNITS
    • _LOVS, _ALERTS, _PARAMETERS
    • _RELATIONS, _VISUAL_ATTRS, _RECORD_GROUPS
  7. Materializa pré-requisitos em .specs/codebase/knowledge-base/ se ausentes.
  8. Invoca skill engenharia-reversa-forms Passos 2–6 (Inventário UI → Triggers → Dependências → Smells/Riscos → Painel de Decisão).
  9. Gera artefato reversa-<MODULO>.md seguindo templates/reverse-engineering-forms-template.md (a criar na primeira execução).
  10. Atualiza índice README-modulo.md listando todas as revisões.
  11. Atualiza catálogos: catalogo-objetos-plsql.md (packages chamados pelo Forms), pendencias-abertas.md, riscos-ans.md.
  12. Apresenta Painel de Decisão ao TL com sinopse, regras prioritizadas, lista de marcadores e recomendação (modernizar/manter/deprecate).
